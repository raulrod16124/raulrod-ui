## Usage

Wrap your app with `ToastProvider` and call `useToast` from any child
component:

```tsx
import { Button, ToastProvider, useToast } from "@raulrod/ui";

function NotifyButton() {
  const { toast } = useToast();
  return (
    <Button
      onClick={() =>
        toast({
          title: "Changes saved",
          tone: "success",
        })
      }
    >
      Save
    </Button>
  );
}

function App() {
  return (
    <ToastProvider>
      <NotifyButton />
    </ToastProvider>
  );
}
```

### Placement and size: the stack is bounded by the viewport

The stack is `position: fixed` in the **top-right corner of the screen**, so its
geometry comes from the viewport and not from your layout — a narrow container
around your app changes nothing about where notifications land. It is inset 16px
from the top and from both inline edges, and capped at 384px (6 × `space-16`), so on
a wide screen notifications are a card rather than a column, and on a 320px phone the
column is 288px with the same 16px gutter on each side.

The stack is also bounded in the **block** direction: at most the viewport height
minus 16px top and bottom, and it scrolls vertically when there are more
notifications than fit. That bound is why a long description stays reachable —
before it, a single long notification rendered taller than a short screen and the
bottom of its text simply left the viewport with nothing to scroll through. Every
toast carries its own dismiss button, so <kbd>Tab</kbd> reaches notifications inside
the scrollport and the browser brings each focused one into view.

Order is newest-first, so the notification you raise first is the one at the bottom.

## Accessibility

- Tone drives the role: `info`/`success` → `role="status"` (polite);
  `warning`/`destructive` → `role="alert"` (assertive).
- `title` is required so the screen reader has content to announce.
- Toasts are rendered through a portal into a viewport region.
- The stack's scrollport is keyboard-reachable: every toast carries a focusable
  dismiss button, so `Tab` moves focus through the notifications that are scrolled
  out of view and the browser scrolls each focused one into view.
- The fixed region is `pointer-events: none`, so it never blocks clicks on the page
  underneath; each toast re-enables pointer events on itself.

## Trade-offs / Limitations

- **Imperative API.** Toasts are pushed via `toast()`, not declared as JSX. This
  matches real-world async feedback (fetch responses, mutations) but is less
  “React-idiomatic” than a declarative queue.
- **No rich content animations.** Entrance/exit motion is present, but complex
  reordering or progress-toast patterns are out of MVP scope.
- **Tone drives duration defaults.** Status tones auto-dismiss using the
  provider `duration`; alert tones default to persistent. A per-toast `duration`
  always wins.
- **Provider must be mounted once.** Calling `useToast` outside the provider
  throws at runtime; the TypeScript contract cannot enforce this at compile
  time.
- **Placement and size are not configurable.** The stack is always top-right,
  16px from the edges, at most 384px wide, and bounded to the viewport height. A
  bottom-left notification rail or a wider column would each need a placement
  decision for the whole system, not a prop.
- **A very tall toast scrolls rather than truncating.** The bound keeps the stack on
  screen; it does not make a 500-character description fit in 288 × 328px. Shorten
  the copy if the whole message matters — a notification is a summary, and the
  durable place for the detail is wherever the action leads.
